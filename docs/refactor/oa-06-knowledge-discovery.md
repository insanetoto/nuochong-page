# 首个业务需求评审草案：公司规章制度知识库

状态：待产品负责人确认，非开发授权。2026-10-30用户提出：使用者为公司全体人员，初期纳入公司规章管理制度，为后续 OA 建设提供制度依据。本次只给出范围与待决策项，不恢复旧知识库原型、不导入真实制度。

## 首期目标和使用者

员工可按授权检索当前有效制度，查看原文、发布日期、生效日期、版本及来源，并获得有引用的 AI 回答；找不到依据时明确表示不足，不虚构制度。制度负责人负责维护来源和版本，发布权限由公司指定；系统管理员负责身份及运行，管理员权限不自动授予员工。具体岗位与审批人待指定。

## 推荐首期范围

1. 制度负责人提交公司授权的制度文件及元数据，进入待审核状态；支持的文件格式、大小和批量导入量在设计评审时确认。
2. 经指定负责人审核并发布后，向授权的全体员工开放；草稿、待审和撤回版本默认不可被普通员工检索或被AI引用。权限由服务端统一验证，搜索索引和片段不得绕开原文权限。
3. 展示制度标题、发布部门、唯一编号、版本、生效/失效日期、状态、来源和原文；版本更新保留历史，旧版本不会作为现行制度回答。冲突或无效日期应阻止发布并提示处理。
4. 检索返回原文位置和版本，AI答案逐条引用可访问的来源；无法证实或引用不可见时拒绝确定性结论，明确提示查阅原文或联系负责人。输出不替代制度发布与人工审批。
5. 每次导入、审核、发布、撤回、索引与访问有必要的脱敏审计；不得在日志记录全文、凭据或员工原始问答。恢复、索引重建和权限撤销需测试。

以上是待确认的建议范围，不预设全部制度对所有人公开；实际可见范围取决于制度密级与公司政策。第一阶段不包括员工档案、培训、工单、通用网盘、自动审批或制度自动起草发布。

## CLI 优先和扩展接口

能力先定义版本化 commandId、输入/输出 schema、授权、幂等及副作用，再由 Web、CLI 和受限 MCP 共享同一服务。候选能力 `knowledge.documents.list/get/search`、`knowledge.documents.submit/review/publish/withdraw`、`knowledge.answers.ask` 仅为 planned，命名/schema/发布与撤回审批流程须评审；未实现时不可返回模拟成功。对写操作不允许 `--yes`、dry-run 或模型工具调用绕过审核和幂等。

## 评审验收草案

- 使用合成制度：草稿不可被员工读取或搜索；已发布且授权的现行版本可查、可引用；未授权者无搜索结果及下载权限。
- 发布新版本后，检索和AI答案引用新版本；过期、撤回、重复与冲突版本不能误判为现行制度。
- 有依据的回答附原文位置与版本，无依据明确说明；撤权后 API、CLI、MCP 与UI一致拒绝，拒绝不触发业务写入。
- 审批、发布、撤回幂等并可审计；索引重建/进程重启后权限及版本不倒退；真实文件不进入测试夹具或日志。
- 员工能从原文链接核对制度，屏幕与 CLI 显示清晰的有效期和来源；正式上线需单独决定真实部署、数据迁移和验收。

## 产品负责人待确认

制度归口/审核发布人是谁；制度是否存在部门或密级范围；文档格式、首批数量和已有权威来源；历史版本的员工可见策略；AI回答是否需单独免责声明或人工确认；制度生效时间及相互冲突时的裁决规则。确认后再细化数据模型、分批任务和工期，不能把本草案当作现有已实现功能。
