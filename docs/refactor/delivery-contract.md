# 从产品需求到独立任务的交付规范

2026-11-15 · 负责人要求优化任务下达。ChatGPT负责需求、业务/功能/原型、架构、任务与预审；DeepSeek负责代码、迁移和测试。适用于后续新任务及尚未完成工作的重新交接。已批准的产品原型/契约不因此重新审批；本规范不改变运行准入、官网基线或发布范围。

## 1. 核心规则

一个开发Issue只交付一个可独立验收的结果。必须说明目的、前置条件、操作步骤、结果、禁止副作用及测试。不得开工后在Issue内临时增加A/B/C等可独立开发的子任务。实施步骤可以编号，但每步必须服务于同一验收结果，不具有独立发布出口。

“独立”指完成后能在已验收依赖上独立验证、合并、定位失败和回退，不指零依赖或必须并行。依赖必须指向具体Issue的已合并提交/版本化接口，不依赖对方尚未审核的开发分支。共享文件不等于业务依赖，须单列文件占用顺序。

跨多个目标的总目标使用Tracking类型，只汇总正式Issue和产品验收，不领取代码、不计为一个开发任务。发现一个任务必须再拆时：暂停新增范围，先创建不同编号的正式Issue并逐项迁移AC，再恢复；不能悄悄沿用同一编号下的字母切片。

## 2. 创建开发任务前必须完成的设计包

| 顺序/主责 | 必备产物 | 必须明确 | 设计出口 |
| --- | --- | --- | --- |
| 需求梳理/ChatGPT | REQ清单、场景与优先级、非目标 | 谁在什么条件下解决什么问题；成功与失败如何判断；受影响用户/数据；本轮范围 | 负责人确认需求方向；沿用已确认需求须引用证据，不重复询问 |
| 业务设计/ChatGPT | BIZ流程、状态表、权限矩阵 | 入口→动作→分支→终态；谁有权；审批；失败/取消/撤权/重试/恢复；不变量 | 每条需求都有完整流程，没有让实现者猜的状态或权限规则 |
| 功能设计/ChatGPT | FUNC清单、版本化commandId、schema及错误表 | 输入/输出/错误；API/CLI同权；幂等键生命周期；原子提交/授权串行点；数据/迁移/兼容/配额/回退 | 逐功能有可调用契约和可观察结果；未实现标planned |
| 原型与交互/ChatGPT | 可点击原型固定SHA、页面/交互状态表 | 路由、逐步/返回/刷新、空/错/慢/部分成功、角色与撤权、焦点/键盘/窄屏；与FUNC映射 | 页面动作能追溯到真实契约；视觉批准不等于运行功能验收 |
| 技术与验证设计/ChatGPT，DeepSeek反馈可测试性 | 决策、依赖图、夹具、故障屏障/测试计划 | 真实入口、事务/持久状态、异步交错、资源上限；如何确定性复现；如何证明断言能发现坏行为 | 已知反例写在开工前；设计无法验证先修设计，不边编码边猜 |
| 任务拆解/ChatGPT | 独立Issue、允许文件、AC与测试矩阵 | 结果/步骤/依赖/交付/禁止范围；每条AC有手段和期望 | 通过下述Ready检查，才可领取 |

追溯链必须完整：REQ → BIZ → FUNC/command → 原型页面/动作（非UI填不适用）→ Issue → AC → 用例/证据。禁止只贴几份长文档让实现者自行拼接需求。每个设计包提供当前版本及摘要；历史文档明确历史状态。冲突由ChatGPT解决，DeepSeek不自行选择宽松解释。

## 3. Ready检查：缺任一必填项不下达实现

- 一个明确用户/系统结果和一个独立关闭条件；不存在“先做一部分，剩下以后再定”。
- 已确认REQ/BIZ/FUNC及原型版本；所有待定点有决定或显式排除。探索本身可独立建任务，产物是决策/实验报告，不冒充业务实现。
- 所有依赖有精确Issue、提交、可用接口和验收事实；未满足的任务保持Blocked，不把父Tracking关闭当技术依赖。
- 明确实现步骤、允许/禁止目录、共享文件责任；迁移编号在领取时登记，不假定旧编号永远可用。
- 每条AC给出输入/角色/原状态/动作/交错/预期/禁止副作用/可观察字段；业务数值来自确认基线，不临时发明SLA。
- 每条AC映射实际测试层、夹具及执行命令。测试文件尚未创建可给拟定路径，实施后必须改为真实证据。
- 高风险项预先指定代表反例和验证器敏感性检查；不能只列“权限正确、恢复正常、CI通过”。
- 实现者先提交理解回执与测试映射；ChatGPT一次预检验收可执行性。普通实现选择无需再请负责人批准；新的产品/权限/状态语义先修设计。

## 4. 测试证据格式与判定

| 字段 | 必填内容 |
| --- | --- |
| AC/用例 | 稳定编号及独立预期值；不能从实现输出反推正确答案 |
| 输入 | 合成夹具版本/hash、角色/权限、原始数据库/任务状态 |
| 执行 | 命令、环境、基础/head SHA；故障屏障/注入位置及顺序 |
| 预期 | 返回、DB字段、事件/对象/批次/线程结果，以及禁止新增/泄漏/重复写 |
| 实际 | 测试文件/用例、结果、固定运行链接；未运行/不适用必须注明理由 |
| 敏感性 | 对高风险保护退化后相应负例确实失败；临时变异不进入提交 |

示例：恢复不是“重启后能跑新任务”，而是“原file=parsing时强杀→确认exit→同schema/root重启→同file/batch收敛→显式retry后单一来源/片段集”。取消不是“函数返回cancelled”，必须同时验证DB文件、批次、API结果、后续业务写入和线程停止。幂等不是“有一个key字段”，必须验证服务端提交后响应丢失、相同输入重发、输入改变的显式新操作，以及只生成一个批次。

使用屏障/有界状态等待，不靠短sleep碰时序。CI总数不代表AC覆盖；Build成功不代表浏览器或原生PG验证。核对实际head、触发事件、目标base、步骤是否运行；Skipped/未触发不能算通过，保留首次失败记录。macOS截图不替代Linux视觉验收。

## 5. 实施和审查流程

1. 领取一个Ready Issue，记录实际执行者、依赖验收、基线SHA、分支/目录及文件占用；不从未审任务分支堆叠新实现。
2. 回执逐项列“目标理解→AC→拟定测试/夹具/故障屏障”。设计缺口由ChatGPT在批量实现前处理。
3. DeepSeek完成一个结果的代码和测试；提交前自查全AC，列失败/未运行项；存在未完成AC不得把Issue改为Done。
4. ChatGPT首轮按任务风险矩阵完整审查，一次列全已发现的问题；修订轮先验证旧反例、同类旁路和新增回归。
5. 每条反馈注明“原AC遗漏/修复引入回归/新增需求”。前两类可阻塞；新增需求进入独立Issue，禁止追加入原任务当缺陷。发现原设计欠缺先承认并给明确修订，不让实现者猜。
6. 同一不变量两次修订仍遗漏，先停扩大范围，补最小确定复现与原因/测试方案，再继续；不以连续重跑碰绿、不用新增测试总数代替结论。
7. 负责人已授权：技术审核及有效CI通过、head一致后自动合并任务目标集成分支，独立任务满足全部AC后关闭。代码审核、人工产品验收、环境发布分别记录，不代签未进行的体验验收。需要人工验收的任务在卡片中预先写明，不到合并时突然增加门槛。
8. 任务合并后更新依赖及任务台账；部署沿用单独发布授权，不向main/test擅自推送。

## 6. 任务尺寸与拆分检查

不按文件数、代码行数或固定天数机械切分。若存在两组不同的关闭条件、需要独立的验收环境，或某组结果不依赖另一组实现即可合并，通常应在开工前拆成不同Issue。若拆后只剩“写一张表/画一个按钮”且无法验证真实结果，则拆分过细，应和同一行为的最小闭环合并。

默认一个Issue对应一个结果PR，内部代码提交可多次。任务开工后禁止用A/B/C或未登记的“阶段一”替代正式Issue。确需多PR，必须在下达前列清各自结果与独立正式任务；Tracking只负责汇总。

## 7. 效果度量

从新任务起记录：Ready后仍需澄清的设计缺口次数、首次提交缺失AC数、同一缺陷重现次数、修复引入回归次数、审查轮次/等待时间、逃逸到测试环境的缺陷。区分新需求和缺陷返工，不用强压“一次通过率”驱动隐瞒问题。先建立样本，再比较改进，不虚构改善比例，也不承诺零复审。
