# ADR-011：三产品插件体系与企业 LLM Wiki

## 决策建议

1. 企业知识库、企业 AI 工具、培训和考试复用 DeepSeek Harness；用产品插件承载业务，用受限 Harness 工具适配调用领域 API。身份、授权、任务持久层和审批是不可被插件绕过的平台核心。
2. 采用模块化单体 + 独立 Worker，先复用 PostgreSQL 和私有对象存储；不先建微服务、图数据库或独立向量集群。
3. 知识库采用 LLM Wiki：不可变来源、可版本化的 Markdown 知识页、schema、目录及维护日志；通过 ingest/query/lint 累积知识。企业适配增加审校发布、来源有效期、ACL、撤回和依赖失效。
4. 原文是制度权威，AI 知识页为可核验解读；模型产出进入变更集，经人工发布后才面向员工。问答沉淀同样走候选变更，不能问一次就自动修改制度依据。
5. 数据库保存业务 manifest/发布状态/审批/依赖/ACL；对象存储保存不可变内容。Markdown 导出用于移植与备份，不与数据库构成两个可任意修改的主库。
6. 公司服务端提供 DeepSeek 凭据；演示不要求访客 DeepSeek 登录或 BYOK。未来员工入口采用产品壳，不能把原生 owner 会话当作公司用户。

7. 部门、人员、角色授权管理封装为公司共享插件，由三产品组合使用；外部目录为可选适配。产品声明自身权限和资源类型，不能各自维护人员/角色主库；可信核心继续强制执行授权。依赖缺失时拒绝，管理插件禁用不等于关闭权限校验。详见 [共享组织与权限设计](../product/shared-access/design.md)。

## 方案取舍

仅向量 RAG 上手快，但不足以表达持续整理的知识页、冲突和审校；纯共享目录 Wiki 难以保证多用户授权和并发发布。推荐受控 LLM Wiki 加权限检索：默认结构化/全文检索，向量召回在实测有必要时作为可重建插件索引加入，任何召回方式都不能替代制度原文、权限或有效期。

使用插件增加清晰的模块边界，也增加兼容、生命周期和迁移成本；首期仅批准的第一方插件，不建设开放插件市场。保留上游原生管理员页面；产品界面通过独立壳和插件路由实现，不 fork 上游 UI。
